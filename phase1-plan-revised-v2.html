  • 前 4 轮只有日志 commit，是因为那些轮次是只读评审 / 审计、没有代码改动，不是规则禁止。
  • 本轮没有修改任何业务代码，所以「擅自提交代码」这件事没有发生。按你的长期口径，本轮新增的方案文档默认独立提交，日志单独一个 commit，不 push、不改历史；工作区既有的 46 项未提交改动仍然不清理、不覆盖、不代为提交 —— 这一条与任务单「不覆盖或清理现有改动」完全一致。

0.2 一处需要同步给 ChatGPT 的事实更正：安全整改的相当一部分被架构变更本身消化了

第 4 轮审计报告（security-audit-report.md）里最严重的两条 ——「任意服务器目录可被扫描」「伪造 fullPath 把服务器上的文件复制进 uploads」—— 都依附于旧的服务器目录扫描接口（/api/scan-folder 与旧 apply-scan）。本轮正式需求改为浏览器上传后，这两个接口按计划下线，风险链随之消失，不需要单独先做一轮「加白名单」的安全整改。

这不是把已发现的问题当不存在，而是把整改分成三档（详见 4.6）：

  • 随链必做：本来就是新功能正确性的一部分（上传权限、文件名、大小、失败清理、批量上限），跟着 S1~S3 一起做，不另立前置任务。
  • 架构变更自动消除：旧扫描/导入接口下线。
  • 按风险排期：默认账号、GET /api/projects 完整 data 回传、导出 zip manifest 字段收敛、CORS 等与本次业务链无直接关系的存量项，排在部门多人试用前或之后，不阻塞原型。

0.3 一处对「共享下载」口径的保留

v1 已核实的结论继续有效：本项目的读侧定位是所有已登录用户可下载共享文件，因此 GET /api/files/{id} 等接口「登录即可读」是符合定位的，不能简单加一层角色判断，否则反而破坏共享。真正要收敛的是项目列表与导出包里回传的字段范围，属于「按风险排期」而非「开工阻断」。

一、正式需求（业务语言）

一句话：用户在自己电脑上选一个资料目录 → 网页里预览并勾选要上传的文件 → 上传到服务器 → 部门其他同事能在系统里查到并下载。

明确否定：不要求任何人先把文件拷到服务器共享目录；不设「服务器目录白名单」这类前置条件；不要求先完成一轮全面安全整改才能开始。

1.1 本期必须能跑通的完整业务链

用户本机选目录 → 预览文件 → 选择上传 → 服务器保存 → 其他用户查找和下载

这条链是本期唯一的主线，后续所有技术决策都以「这条链是否可靠、好用、易维护」来判断。

1.2 打通之后必须能做到的四件事（来自 GPT 第 6 轮，逐条按使用场景验收）

场景用户想做的事验收时怎么判「做到了」
A查找某个项目的暖通施工图选定项目、阶段，能列出该阶段全部文件并下载其中一个
B查找其他项目中同类型的设计文件，供参考复用不切换项目就能看到别的项目的同类文件，并能下载
C根据系统、阶段、版本等条件筛选文件能用条件组合缩小范围，结果条数与预期一致
D将来迁移服务器上的文件存储位置时，原有文件记录和检索功能还能正常工作搬迁演练后，历史文件仍可按原入口下载、检索结果不丢失
这四件事对应 MD_collect/Needs/需求说明书_V3_1.md:229-239 的 FR-12。按 ChatGPT 的要求，验收只看这些操作能不能完成，不以「数据库是否新增了字段」作为通过标准。

  • 不做 DWG 图框自动填充、设计说明模板填充（仍为占位能力，另立阶段）。
  • 不做文件内容对比、在线预览 Office / CAD 图纸。
  • 不新建一套分类字段体系或枚举字典表（见第三章）。
  • 不改物理存储目录结构、不重建应用、不做整体数据迁移。
  • 不实现 Tauri / 桌面客户端（只做评估与推荐，见第二章）。
  • 不做全面权限体系重构、不做完整测试平台 / CI 建设。
  • 跨项目复用与追溯（FR-12）可以排在本期主链之后完成，但仍是正式必做需求，不从需求基线中删除。

二、选型评估：继续用网页，还是改用 Tauri 桌面客户端

本节是任务单第 1 条明确要求的评估。结论先给：本期推荐继续用网页，Tauri 作为「触发式备选」认真保留但不迁移、不开发。 以下事实来自当前工作副本只读核查。

2.1 四个维度对比

考虑因素继续用网页（浏览器本机选目录）改用 Tauri 桌面客户端
用户操作体验零安装，打开 http://服务器IP:3001/ 就能用；浏览器里选目录 → 勾选 → 上传。局限：不能记住上次选的目录、不能后台常驻扫描；内网是纯 HTTP（非安全上下文），showDirectoryPicker() 大概率不可用，只能用 webkitdirectory 选目录可记住常用目录、可增量扫描、本机文件操作更自然、大批量更稳；但每台电脑要装客户端、要处理升级
开发复杂度复用现有 React 19 + FastAPI；已有的「浏览器真上传字节 → 落盘 → files 表 → 过程记录 → 下载」链路完整存在（src/api/index.ts:63-75 → server/app.py:2637-2809）。要补的是目录选择、分批、进度、失败隔离当前工作副本没有任何 Tauri / Electron / Rust / src-tauri / Cargo.toml 骨架，需从零建客户端工程；服务端上传接口、授权、数据层的改造一项都省不掉（数据与权限都在服务端 SQLite/磁盘，server/app.py:39-41,860-942,1399-1424）
维护成本单进程 FastAPI 同时托管前端 dist/（server/app.py:204-205,3833-3858）；更新只替换服务端一处，用户刷新浏览器即可；DEPLOY_INTERNAL.md:5-11 明确「不需要前端开发服务器，也不需要 Node.js」额外增加：安装包生成与签名、每台客户机安装 / 升级分发、客户端与 /api 的版本兼容矩阵、自动更新通道。现有工程无 CI、无 .sh/.ps1 多平台脚本、package.json:4 version 仍是 0.0.0，发布体系要从零建立
安全性服务端仍是唯一信任边界；上传需校验登录 + 项目编辑权限（现有 :2647,2664-2668 已有）、文件名去路径（:2339-2341 已有）、大小（:48 100MB）；批量场景需补请求体总大小、单次文件数、类型白名单、幂等不会因为换成桌面客户端就省略服务端权限校验；反而多出客户端分发供应链、本地文件访问范围、客户端凭据存储等新的安全面

2.2 成本判断（一句话）

两条路线要改的服务端上传链路和校验是同一份；Tauri 只额外替换了「前端宿主 + 本机读取方式」，却要新增一整套当前完全不存在的安装包 / 签名 / 分发 / 升级体系。对「先让工具逐步可用」这个当前目标，网页方案的边际成本明显更低。

2.3 推荐与理由

本期选网页方案：以 <input type="file" webkitdirectory> + webkitRelativePath 拿到本机目录树与相对层级，勾选后分批上传到现有上传接口。理由三条：

  1. 零安装、零分发，符合内网部门共用的部署现状；
  2. 现有上传链路可复用，改造集中在前端组件与服务端批量校验；
  3. 能最快把 1.1 的业务链跑通，用真实反馈决定后续，而不是先押注一次客户端迁移。

需要实测确认（静态代码无法定论）：目标 Chrome / Edge 在 http://服务器IP:3001/ 下 webkitdirectory 是否正常、中文与长路径的 webkitRelativePath 是否完整、单次上千文件的浏览器内存表现。文档里没有指定浏览器版本，这三项要列入 S1 的实操验收。

2.4 Tauri 的触发条件（满足两条以上再正式评估迁移）

  • 单次经常超过 100MB 或上千个文件，浏览器分批 / 内存表现不达标；
  • 需要记住本机目录、做增量扫描或后台定时扫描；
  • 需要断点续传、离线预处理、本地缓存等浏览器难以稳定提供的能力；
  • 部门长期大量使用本机文件，客户端安装分发成本能被摊薄。

当前决定：不迁移、不开发完整客户端、不引入任何桌面依赖；本结论在待决策项 Q7 里请你确认。

4.1 S0 · 保存现状（不覆盖、不清理、不提交既有改动）

  • 做什么：把当前工作区（含 46 项未提交改动、server/uploads/、server/hvac.db 等数据）原样复制成一份带日期的快照，并写一张「当前如何启动」的说明页。
  • 明确不做：不 git add 那 46 项、不清理、不覆盖、不重组目录、不为了「建立基线」而重写任何现有文件。
  • 与提交的关系：快照是副本，与 Git 提交无关；本轮新写的方案文档按你的长期规则独立提交（见 0.1）。

  • 配套验证：一次真实启动记录（截图 / 日志），不要求自动化测试。

4.2 S1 · 本机目录选择与预览

  • 功能目标：不再让用户输入服务器路径，改成在自己电脑上选文件夹；网页列出目录里的文件与相对层级，能勾选、排除、批量改归类。
  • 用户操作：点「选择文件夹」→ 浏览器弹目录选择 → 网页显示文件树 → 勾选 / 取消 / 按阶段或类别批量归类 → 导入前看到汇总（共 N 个、选中 M 个、预计大小）。
  • 交付结果：新的目录选择组件 + 预览筛选界面；旧「输入服务器路径」的扫描页从菜单下线（接口一并下线，见 0.2）。
  • 单独验收：用一份真实资料目录（含中文名、长路径、4 层以上、隐藏文件、空目录、同名文件）走一遍，列出文件数与人工清点一致，无静默丢失；记录浏览器版本。
  • 配套测试：目录树构建、筛选、全选 / 反选、排除、汇总计数 —— vitest 单元测试（可用构造的 FileList 假数据，不需要真实浏览器）。

4.3 S2 · 上传到服务器

  • 功能目标：把勾选的文件真正传到服务器，落到现有项目 / 子项 / 过程记录里，别人能看到。
  • 用户操作：选目标项目与子项 → 点上传 → 看逐文件进度与结果 → 失败项单独重试。
  • 交付结果：复用现有上传接口（server/app.py:2637-2809）与 files 表登记；补分批上传、进度显示、失败隔离、同批次重试不产生重复记录。
  • 单独验收：上传 3~5 个文件（含 1 个中文名）→ 换另一台电脑、换另一个账号登录 → 能查到并下载，内容与原件一致；中途断网重试，不产生重复文件、不留半截文件。
  • 配套测试：接口测试覆盖「未登录被拒」「无编辑权限被拒」「重名 / 重复提交」「单文件超限」「部分失败」；前端补进度与重试状态机用例。

4.4 S3 · 查询与下载（含跨项目检索）

  • 功能目标：把 3.3 的四个场景做成可操作的界面。
  • 用户操作：按项目 / 阶段 / 类别 / 版本条件找文件 → 跨项目看同类文件 → 单文件下载或打包。
  • 交付结果：一个文件查询能力与一个检索视图；沿用现有分类名称，不新建分类体系。
  • 单独验收：按 3.3 表逐条走一遍；特别检查 B 场景确实能命中其他项目、C 场景结果条数与人工清点一致。
  • 配套测试：查询接口的条件组合、空结果、跨项目范围、字段范围；前端筛选控件用例。

4.5 S4 · 小步补齐与试用前检查

  • 做什么：按实际试用反馈补常见误操作、上传失败、超大文件、重复导入的提示与处理；完成「多人试用前检查表」。
  • 底线（对应 ChatGPT 保留的那一条）：正式给部门多人使用前，至少确认普通用户不能通过错误操作破坏其他人的文件、上传与下载符合预期。
